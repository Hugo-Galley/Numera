# Numera — releases

## Principle

A release = a `vX.Y.Z` tag on `main`. The tag triggers `.github/workflows/release.yml`: check (commit on `main`, CI green) → 3 multi-arch images on GHCR (`numera-backend`, `numera-frontend`, `numera-mcp`), pushed by digest, scanned by Trivy in amd64 and arm64, then tagged `X.Y.Z`, `X.Y` and `latest` only if the tag is the highest version (`scripts/release/is_latest.py`) → GitHub Release with notes generated by `scripts/release/release_notes.py` from the Conventional Commits. No hand-written changelog; the quality of the notes therefore depends on that of the commit messages (`type(scope): description`, the body explains why).

## Writing for the notes

The PR title (= squashed commit) becomes a public line: a short present-tense sentence, user-side ("Upcoming view of future transactions"), not the technical detail. `(#N)` is added by GitHub and rendered as a link.

Rendering (`scripts/release/release_notes.py`; section headings are generated in French by the script and quoted verbatim):

| Section | Content |
|---|---|
| Breaking changes ("Changements incompatibles") | any `!` / `BREAKING CHANGE` commit, at the top |
| ✨ "À la une" (highlights) | up to 3 visible `feat`; those with a **first body paragraph** come first and display it (≤ 280 chars, no bullets or signatures) |
| 🆕 "Nouveautés" (new) · 🐛 "Corrections" (fixes) · ⚡ "Performances" | the rest, `**Scope** · Description (#N)` |
| 🔧 "Sous le capot" (under the hood) | `refactor` and tooling scopes (`qualité`, `ci`, `release`, `build`, `tests`, `docs`, `deps`) |

For a new feature to be highlighted well: a commit (or PR) body whose **first paragraph** explains in one or two sentences what it changes for the user, before any technical list. `docs` / `test` / `chore` / `ci` stay silent (apart from tooling scopes on `feat`/`fix`). The note ends with the update command and the "Full changelog" link (comparison with the previous tag). Preview: `make release-check`.

The workflow attaches to the Release a standalone `docker-compose.yml` (derived from `infra/docker-compose.images.yml`, the release version as default of `NUMERA_VERSION`). `install.sh` ("Docker" mode, recommended in the README) downloads it; `infra/docker-compose.images.yml` must stay identical to `docker-compose.prod.yml` apart from `build`/`image`/volumes (`tests/garde_fous/test_compose_images.py`). Any change to `docker-compose.prod.yml` must therefore be mirrored in `infra/docker-compose.images.yml`.

## Autonomy

I decide **on my own** to propose and cut a release when the criteria below are met, without waiting for the user to ask. The user can also ask explicitly ("release", "cut a 0.4"): their version or bump then overrides the computation. They can also say not to release: in that case tag nothing.

Pushing a tag publishes public images and a public release, which is irreversible for consumers: never **delete or move** a published tag. A mistake is fixed by a following version.

## When to release

Release if, since the last tag, `python3 scripts/release/release_notes.py --bump` does not answer `none` **and**:

- the set of changes forms a stable, validated state (`make validate` green on `main`, CI green);
- the last tag is more than a few `fix` / `feat` commits behind, **or** a `fix` corrects a data or security bug (release immediately, without waiting for the batch);
- no half-finished work is on `main` (feature behind a flag, migration to complete).

Do not release: only `docs` / `test` / `chore` / `refactor` (the script answers `none`), red CI, a change in progress in the session that is not validated, or less than a day after the previous release without a critical fix.

## Which bump

While the major version is `0` (current state, no tag before the first release), the rules are the same but we do **not** move to `1.0.0` without the user's explicit agreement (it is a stability commitment).

| Bump | When | Examples |
|---|---|---|
| **patch** | fixes and perf, nothing new for the user | `fix(...)`, `perf(...)` |
| **minor** | new visible feature, new route/page/setting, additive migration | `feat(...)` |
| **major** | breaking: `type!:` or `BREAKING CHANGE:` — route removed/renamed, new or renamed mandatory environment variable, incompatible export/import or backup format, destructive or non-replayable migration, `docker-compose` change requiring user action | |

`release_notes.py --bump` applies these rules to the commits. Read it with judgement: a `feat` that changes an existing behaviour incompatibly is a **major** even without `!`. In that case, correct the decision by hand and say so in the report (do not rewrite history).

## Procedure

1. Clean `git status`, on `main` (or `release/X.Y` for a fix to an older version, see `docs/WORKFLOW_GIT.md`), up to date with its `origin`; `git fetch --tags`.
2. `make validate` green (otherwise no release).
3. `make release-check`: suggested bump, next version, notes preview. Decide according to the sections above.
4. `make release V=X.Y.Z`: checks (clean, on `main`, tag free, version > last tag), creates an annotated tag and pushes it.
5. Follow the workflow (`gh run watch`), check that the Release exists, that it carries `docker-compose.yml` as an attachment, and that `docker pull ghcr.io/hugo-galley/numera-backend:X.Y.Z` works; at the first tag, make the 3 GHCR packages **public** (package settings → Change visibility), otherwise `docker pull` asks for authentication.
6. Report to the user: version, bump chosen and why, release link, what was not verified.

## If the workflow fails

- `verify`: CI is not green on the tagged commit → fix through a PR to `main` (or `release/X.Y`), then a **new tag** (next patch). Do not force.
- `images` or `release` failing transiently: rerun the job (`gh run rerun --failed`), without touching the tag.
