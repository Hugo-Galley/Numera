# Frontend — conventions (React 19 / Vite / TypeScript / Tailwind / shadcn)

Complète le `CLAUDE.md` racine. Procédures : skill `numera-frontend`. Le frontend est **purement présentatif** : aucun KPI calculé ici, tout vient de `/analytics/*`. Exceptions admises (présentation, pas un KPI) : parts en % d'un graphique, tri, et calculs sur les lignes déjà chargées d'une liste. Restent à déplacer au backend : variations de la page Comparaison, total du drill-down (affiché seulement si la liste n'est pas tronquée à 500), répartition fonds euros / UC d'une assurance-vie, sous-totaux annuels de l'échéancier de prêt, valeur totale des positions filtrées, moyenne en mode recherche.

## Structure

- `App.tsx` : react-router v7. `/login` public ; le reste sous `ProtectedRoute` + `AppLayout` (Sidebar, Omnibox). Routes (pages chargées à la demande, `React.lazy`) : `/`, `/accounts`, `/accounts/:id`, `/savings`, `/investments`, `/month/{bilan,revue,comparaison}` (`MonthHub.tsx` ; bilan = `MonthlyReport.tsx`, sections dans `components/monthly-report/` ; revue = `MonthReview.tsx`, pop-up `components/month-review/MonthReviewPopup` sur le Dashboard), `/recurring` (« Échéances », onglets `?tab=` dont `calendar` = `Calendar.tsx` embarqué et `salary` = `components/recurring/IncomeTab` : Salaire ou Aides perçues via `?vue=aides`), `/audit` (Centre d'Actions, pastille d'actions urgentes dans la Sidebar), `/wrapped` (bilan annuel, `Wrapped.tsx` : récap + story plein écran `components/wrapped/WrappedStory`), `/tools`, `/tax` (Fiscalité), `/classement` (catégories, tags, marchands, règles), `/settings` (4 onglets : general, notifications, security, data ; anciens `?tab=` redirigés dans `Settings.tsx`). Anciennes adresses `/report`, `/month-review`, `/comparison`, `/calendar` redirigées (`RedirectKeepingSearch`). Route inconnue (connecté) → page `NotFound` dans le layout, adresse inchangée, lien « Retour au tableau de bord ». Sidebar : 3 groupes fixes, 12 entrées ; une nouvelle page va d'abord dans un onglet existant si elle s'y rattache.
- Plafond de 350 lignes par fichier (baseline vide, `make check-size`). Une page trop longue devient un dossier `pages/<Page>/` avec `index.tsx` (composition, retours anticipés), un composant par section / dialogue recevant `ctx`, hooks `use*.ts` pour l'état et le chargement (modèle : `pages/AccountDetail/`) ; un gros composant devient `components/<domaine>/<Composant>/` dont `index.tsx` garde le même export. Un petit dépassement se règle en sortant un utilitaire ou un sous-composant dans un fichier voisin (ex. `analytics/sankeyLayout.ts`).
- `providers/` : `AuthProvider` (token en `localStorage`, `useAuth()`), `UIProvider` (thème, mode confidentialité `isPrivacyMode`, état de l'omnibox), `ConfirmProvider` (`useConfirm()`, boîte de confirmation).
- `lib/api/<domaine>.ts` (`accounts`, `analytics`, `classement`, `investments`, `loans`, `monthReview`, `recurring`, `reimbursements`, `savings`, `settings`, `transactions`) : une fonction par route (`getAccounts`, `patchAccountsById`, `getTransactions(query)`…), générique `<T>` à l'appel, `query` (« ?a=1 ») ajouté tel quel à l'URL. Les pages et hooks passent par elles ; une nouvelle route y ajoute sa fonction. Elles reposent sur `lib/api.ts` : `api.get/post/put/patch/delete` + `apiFetch`. Ajoute le Bearer ; sur `401` (ou `403` hors `/auth/token`) vide la session et redirige vers `/login`. `API_BASE` : `VITE_API_BASE` si défini, sinon `http://localhost:8001` sous le serveur de dev Vite, sinon `/api` (build servi par nginx, même sur localhost → `backend:8001`). Erreurs levées en `ApiError(status, message, detail)`. **Cache de lecture** (`lib/apiCache.ts`, TanStack Query) : `api.get` ressert 30 s une même URL sans requête (lectures simultanées dédoublonnées, copie rendue : on peut la modifier), toute écriture (`post/put/patch/delete/upload`), déconnexion ou 401 l'invalide. Un bouton « Actualiser » / « Réessayer » ou un `reload()` qui relit sans écrire doit appeler `resetApiCache()` d'abord, sinon il resservirait la même réponse.
- Découpage du bundle : `build.rolldownOptions.output.codeSplitting.groups` dans `vite.config.ts` (Vite 8 / Rolldown : `rollupOptions` et `manualChunks` sont dépréciés ; chunks `vendor-react`, `-router`, `-radix`, `-charts`, `-date`, `-ui`). Piège : avec `includeDependenciesRecursively: false` (voulu, sinon le groupe aspire des modules partagés et `vendor-charts` finit préchargé à l'entrée), les dépendances de recharts (d3, lodash, eventemitter3…) doivent être **listées explicitement** dans le groupe `vendor-charts`, sinon elles tombent dans un chunk de page et créent un cycle d'import : le build passe, les tests et `vite dev` aussi, mais la production plante (`TypeError: Ie is not a function` sur les pages à graphiques). Après toute modification des groupes ou ajout d'une dépendance : `npm run build`, contrôler que `vendor-charts` (~140 Ko gzip) ne figure pas dans les `modulepreload` de `dist/index.html`, puis ouvrir une page à graphiques dans le **build** (`vite preview`), pas seulement en dev. Vite et `@vitejs/plugin-react` montent ensemble (le plugin 6 exige `vite@^8`) ; Node ≥ 20.19 / 22.12 requis.
- `hooks/useSubmit.ts` : protège un handler async contre la double soumission (`const [handleX, busy] = useSubmit(async () => …)`, bouton `disabled={busy}`). `components/layout/ErrorBoundary.tsx` (global et par route) et `ErrorState.tsx` (message + « Réessayer » : un chargement qui échoue ne doit jamais ressembler à « pas de données »). `lib/storage.ts` : `safeStorage` à la place de `localStorage` (ne lève jamais).
- `types/` (un seul fichier : `diversity.ts`) : les types d'API sont majoritairement définis localement dans les pages/composants.
- `lib/utils.ts` : `formatCurrency(value, currency="EUR")` (locale de l'interface : `fr-FR` ou `en-GB`), `cn()`, `isTokenExpired()`.
- **Langues (i18n)** : français (référence), anglais et espagnol, choix dans Paramètres → Général → Affichage (menu déroulant avec drapeaux), retenu par appareil (`localStorage`, clé `language`), à défaut la langue du navigateur si elle est prise en charge (`fr*`, `en*`, `es*`), sinon anglais. `src/i18n/` : `index.ts` (init `i18next` + `react-i18next`, `setLanguage`, `detectLanguage`), `locales/<fr|en|es>/<espace>.json` (un catalogue par domaine : `common`, `nav`, `auth`, `settings`, `dashboard`, `accounts`, `accountDetail`, `transactions`, `import`, `loans`, `investments`, `omnibox`, `savings`, `recurring`, `reimbursements`, `month`, `classement`, `audit`, `tax`, `tools`, `wrapped` ; un domaine migré = un nouvel espace de noms à déclarer dans `index.ts`), `locale.ts` (`appLocale()`, `dateLocale()`, `monthName()`, `monthShort()`, `percentSuffix()` ; table `LOCALES` par langue), `LanguageBoundary` (remonte l'arbre au changement de langue). Dans un composant : `const { t } = useTranslation("<espace>")`, texte via `t("clé")` (clés **typées** d'après le français : une faute fait échouer `tsc` ; pluriel `clé_one` / `clé_other` + `{ count }` ; variables `{{nom}}` ; texte avec balises ou montant en gras : `<Trans t={t} i18nKey="…" components={{ amount: <span className="…" /> }} />` et `<amount>{{value}}</amount>` dans le catalogue ; mots génériques (Ajouter, Annuler, Enregistrer…) : `common:actions.*`) ; hors composant (`lib/`, classe, constante de module) : `i18n.t("clé", { ns })` **à l'appel**, jamais dans une constante évaluée à l'import (la langue serait figée) : stocker une clé et traduire à l'affichage (ex. `Omnibox/types.ts` → `navigationName`). **Libellé calculé dans une constante d'objet** : utiliser des accesseurs (`get high() { return i18n.t(…) }`, voir `Audit/types.ts`) pour garder l'écriture `LABELS[clé]` sans figer la langue. **Valeurs de données (type `Sortie`, notes générées, noms de préréglages) : jamais traduites** (elles sont enregistrées) ; seules leurs étiquettes d'affichage le sont. Un `t` utilisé dans un `useEffect` / `useCallback` va dans ses dépendances ; ne pas nommer une variable locale `t` (elle masque la fonction). **Ne jamais écrire `"fr-FR"` ni `{ locale: fr }`** : utiliser `appLocale()` / `dateLocale()` pour que dates, mois et montants suivent la langue. Seule l'interface se traduit : libellés, catégories, notes et marchands saisis par l'utilisateur restent tels quels. **Ajouter une langue** : son code dans `LANGUAGES` et ses ressources (`i18n/index.ts`), un dossier `locales/<code>/` (mêmes fichiers et clés que `fr`), une entrée dans `LOCALES` (`locale.ts`), son nom dans `LANGUAGE_NAMES` et son drapeau dans `LANGUAGE_FLAGS` (`DisplayCard`) ; côté backend voir `backend/CLAUDE.md`. Toute chaîne nouvelle va dans tous les catalogues (`i18n/catalogs.test.ts` vérifie, pour chaque langue, mêmes clés et mêmes `{{variables}}` qu'en français). Les tests tournent en français (`test/setup.ts` remet `fr` avant chaque test) ; un test en anglais appelle `setLanguage("en")` et remet `fr` après. **Migration en cours** : Connexion, menus (Sidebar, MobileNav, bannière démo), Page introuvable, états d'erreur, Paramètres (page et carte Affichage) et Tableau de bord (en-tête, KPI, tous les onglets, journal des décisions, bannière de vérification), liste des comptes (création, modification, archivage, rapprochement bancaire), import CSV et saisie d'un crédit sont traduits ; détail d'un compte (en-tête, KPI, graphiques, transactions, filtres, actions groupées, relevés, flux d'investissement), virements internes, découpage, panneau de détail et affichage d'un crédit sont traduits ; page Investissements, positions, dividendes, point zéro, estimation des PRU, profils ETF et Omnibox (⌘K) sont traduits ; Épargne (objectifs, provisions), Échéances (récurrences, abonnements, aides, calendrier) et Remboursements sont traduits ; Mois (bilan, revue, comparaison) et Classement (catégories, tags, marchands, règles, règles de virement) sont traduits ; Centre d'actions (revue des virements, éditeurs) et Fiscalité (enveloppes, déclaration, réglages) sont traduits, ainsi que la bannière hors ligne ; Outils (salaire, télétravail, temps de travail, FIRE, prévision de patrimoine, simulateur avancé) et bilan annuel (récap et story) sont traduits ; les allocations par défaut et préréglages du simulateur gardent leurs noms français (valeurs de données enregistrées) ; les cartes de Paramètres restantes (sauvegarde, découpage des mois, zone de danger, export, historique d'import, connexions, accès MCP, notifications, passkeys, profil, double authentification), les graphiques partagés (treemap, Sankey) et les messages d'erreur du client API (`lib/api.ts`, `lib/passkey.ts`) sont traduits (le mot `EFFACER` à taper pour réinitialiser reste en français : c'est le code attendu par le backend). Tout l'affichage produit par le frontend est donc traduit ; reste le texte envoyé par le backend (lot backend). **Langue envoyée au backend** : `apiFetch` joint `Accept-Language: <langue de l'interface>` à chaque requête et `setLanguage` vide le cache de lecture (un texte serveur mis en cache serait dans l'ancienne langue). Les notifications partent d'une tâche de fond sans en-tête : le choix de langue est aussi enregistré côté serveur (`lib/serverLanguage.ts`, `PUT /notifications/settings {language}`, au clic dans Affichage et à l'ouverture de l'onglet Notifications si la valeur diffère). **Texte venant du backend** (titres et conseils d'`insights`, noms des indicateurs de santé, libellés du Sankey, scénarios de la projection FIRE, messages d'erreur, conseils du rapprochement bancaire) : reste en français tant que le backend ne renvoie pas de codes (lot backend). Une page migrée = un espace de noms, un commit de domaine.
- `components/ui/` : primitives shadcn/Radix (`button`, `card`, `dialog`, `table`, `tabs`, `select`, `sheet`, `sonner`, `skeleton`…). Ne pas les modifier sans nécessité. Ajouter un composant : `components.json` est configuré pour shadcn.
- `components/<domaine>/` : `investments` (dont `PortfolioSummary` valeur calculée / rapprochement, `DividendsCard`, `HoldingsTable`), `dashboard` (KPI, header, `tabs/` = Overview, History, Budgets, Insights, Investments, Merchants, Projections, Subscriptions), `investments`, `settings` (cartes de réglages), `classement`, `import`, `audit`, `tools`, `analytics`, `layout`.

## Règles

- Alias d'import `@/` → `src/`.
- Appels API uniquement via `lib/api/<domaine>.ts` : aucun `api.get/post/…` direct dans les pages et composants (vérifié par `src/test/lib/api/noDirectApi.test.ts`) ; le JWT et la gestion du 401 sont centralisés dans `lib/api.ts`. Uploads multipart : `api.upload(endpoint, formData)` (n'envoie pas `Content-Type`, le navigateur fixe le boundary, mais ajoute le Bearer). Téléchargements de fichiers : `api.download(endpoint)` → `Blob` (jamais `window.location`, qui n'envoie pas le JWT). Les helpers `api.*` ont `T = unknown` par défaut (les wrappers de `lib/api/<domaine>.ts` fournissent le type du contrat). **Contrat API** : `lib/api/generated/` (`openapi.json` exporté du backend, `schema.d.ts` généré par `openapi-typescript`) alimente `ApiResponse<"/accounts", "get">` et `ApiBody<"/accounts", "post">` (`lib/api/types.ts`). Tous les wrappers de `lib/api/<domaine>.ts` sont typés ainsi (réponse par défaut `ApiResponse<chemin, méthode>`, corps `ApiBody<…>`) : un champ renommé côté backend fait échouer `tsc`. Un générique explicite à l'appel (`getX<Foo>()`) court-circuite ce contrôle : le laisser par défaut quand le type de l'API convient. Une réponse sans corps JSON (204) est typée `void`. Route ou schéma Pydantic modifié → `make api-contract` et commiter ; la CI échoue sinon.
- Récupération de données : dans la page, ou dans un hook dédié quand elle est lourde (`components/dashboard/useDashboardData.ts` charge tout le Dashboard avec un `safeLoad` par endpoint pour qu'un échec n'en bloque pas d'autres). Les sous-composants reçoivent des props.
- TypeScript strict, **zéro `any`** (ESLint `@typescript-eslint/no-explicit-any` en erreur, hors `components/ui/` et `lib/api/generated/`) : types de l'API via `ApiResponse` / `ApiBody` (alias dans un `types.ts` voisin), `catch (err)` + `errorMessage(err, repli)`, `unknown` + garde de type pour une donnée libre. Si le contrat OpenAPI ne déclare pas un champ (ex. `price` des résultats de `/market/search`, `metadata` / `samples` du Centre d'Actions), garder un type local minimal avec un commentaire qui le dit, sans toucher au backend.
- Montants : toujours `formatCurrency`. Mode confidentialité : `lib/privacyScanner.ts` détecte automatiquement les montants (devise, milliers, décimales ; DOM, SVG des graphiques, infobulles, inputs) et leur pose `.privacy-masked` ; plus de dévoilement au survol (un champ de saisie se dévoile au focus). `amount-blur` reste utilisable pour forcer le masquage d'une valeur non détectable (ex. pourcentage). `data-privacy-ignore` exclut une zone. Ne pas utiliser `.amount-value` (n'existe pas).
- Dates : jamais `toISOString()` (UTC) pour un champ saisi. `lib/dates.ts` : `nowLocalInput`/`todayLocal` (valeurs initiales), `toInputValue` (API → champ), `toNaiveLocal` (champ → API, sans `Z`), `startOfDayParam`/`endOfDayParam` pour les filtres (le dernier jour inclus). La base stocke des datetimes naïfs affichés tels quels.
- Confirmation avant une action destructive : `const confirm = useConfirm()` (`providers/ConfirmProvider`) puis `if (!(await confirm("…"))) return` ; jamais `window.confirm()` / `alert()`.
- Performance : skill `numera-performance`. Un bouton « Actualiser » / `reload()` qui relit sans écrire appelle `resetApiCache()` (test qui compte les requêtes) ; jamais `queryClient.clear()` ; après un changement de dépendance, contrôler les `modulepreload` de `dist/index.html` et la taille gzip du chargement initial.
- Effet qui se déclenche sur des valeurs précises (changement de compte, de mois, au montage) mais appelle une fonction de chargement recréée à chaque rendu : l'appel passe par `useEffectEvent` (`const reload = useEffectEvent(() => { loadData() }); useEffect(() => { reload() }, [month, year])`), jamais par un `// eslint-disable` ni en ajoutant la fonction aux dépendances (rechargement en boucle). Un setter `useState` s'ajoute tel quel aux dépendances.
- Chargements : une page qui change de mois/compte ignore les réponses obsolètes (drapeau `cancelled` ou numéro de requête) et vide ses données avant de recharger ; `errorMessage(error, repli)` (`lib/utils`) affiche le détail du serveur.
- Retours utilisateur : `toast.success` / `toast.error` (`sonner`) après chaque mutation ; `Skeleton` pendant le chargement ; état vide avec icône + action.
- Contraste : `text-slate-400` (2,6:1) pour les icônes et décorations seulement ; un élément de texte (`p`, `span`, `td`…) qui l'utilise est relevé en slate-500 par `styles.css`, mais écrire `text-slate-500` d'emblée pour tout texte informatif.
- Thème clair / sombre : `UIProvider` (`theme` = light|dark|system, `localStorage`, classe `dark` sur `<html>`, posée avant React par le script d'`index.html`). Les palettes Tailwind (slate, emerald, rose…, `white`) sont des variables CSS (`src/theme-colors.css`, généré par `scripts/gen-theme-colors.cjs`) **inversées en sombre** : écrire les classes habituelles (`bg-white`, `text-slate-900`, `bg-emerald-50`) et **jamais de variante `dark:`** sur ces couleurs (elle s'inverserait deux fois). Les gris en hexadécimal dans les attributs SVG des graphiques sont rebranchés par `styles.css` ; une nouvelle couleur neutre en dur doit être l'une de ces teintes ardoise. Un bloc volontairement sombre dans les deux thèmes (carte héros `bg-slate-900 text-white`, story Wrapped, treemap) prend la classe `theme-island` : il garde la palette claire en sombre au lieu de devenir blanc. Fond de couleur inline (couleur de catégorie/tag) : `text-white` dessus reste blanc en sombre ; pour un repli neutre inline, écrire `rgb(var(--c-slate-500))` plutôt qu'un hexadécimal. Les infobulles Recharts (défaut ou `content` perso) sont surélevées en sombre par `styles.css`, rien à faire dans le composant.
- Icônes `lucide-react`. Graphiques `recharts` (palette Slate / Emerald / Rose / Amber ; tooltips et légendes obligatoires ; éléments cliquables pour drill-down : `useDrilldown().openDrilldown({month, year, label, categoryId | merchantName, accountId})` ouvre le panneau `components/transactions/DrilldownSheet` monté dans `AppLayout`, filtres portés par l'URL `?dd_*`). Sankey/treemap dans `components/analytics`.
- React 19 : un nouveau composant reçoit `ref` comme une prop ordinaire (plus de `forwardRef`) ; les `forwardRef` existants de `components/ui` restent valides (dépréciés, à convertir seulement en retouchant le fichier). Pas de `defaultProps`, `propTypes` ni `ReactDOM.render` ; `useRef` prend toujours une valeur initiale ; JSX via `React.JSX` (plus de namespace global `JSX`). `package.json` force `react-is` ^19 (`overrides`) pour que `recharts` 2 utilise la même version que React. `react-simple-maps` 5 : types livrés, pas d'états `hover`/`pressed` dans `style` (le survol de `WorldMap` est dans `styles.css`, classes `world-map-country*`).
- Formulaires : état local (`useState` + `useSubmit`), validation à la main avant l'appel API. `react-hook-form`, `zod` et `components/ui/form` ont été retirés (jamais utilisés) ; en réintroduire exige de les justifier.
- Code mort : `npm run knip` (`make knip`, `knip.json`) échoue sur un fichier, une dépendance, un export ou un type inutilisé hors `components/ui/` ; baseline à zéro, supprimer plutôt qu'ignorer. Un export utilisé seulement dans son propre fichier est toléré (`ignoreExportsUsedInFile`).
- Mobile (375 px) : toute nouvelle page ou composant suit `docs/MOBILE.md` (navigation `MobileNav`, cartes sous `md`, champs 16 px, cibles 40 px). Le bureau (≥ md) ne doit pas changer.
- Nouvelle fonctionnalité navigable → l'ajouter à la Sidebar et à l'Omnibox (⌘K).

## Vérification

`cd frontend && npm test && npm run build` (ou `make test-front`, inclus dans `make validate` et la CI). `npm test` = `vitest run` (`npm run test:watch` en continu, `npm run coverage` = tests + couverture v8 avec seuils à cliquet dans `vitest.config.ts` (instructions 82 %, lignes 83 %, fonctions 74 %, branches 67 % au 2026-11-12 ; un fichier qu'aucun test ne charge est compté à 0 par v8, donc une page nouvelle sans test fait baisser la mesure) : ne jamais les baisser, les relever quand la couverture progresse ; vérifié par `make coverage`, `make validate` et la CI). `npm run build` = `npm run typecheck && vite build` ; `typecheck` passe `tsc` sur l'app (`tsconfig.json`, qui exclut les tests) puis sur les tests (`tsconfig.test.json`, types `vitest/globals` et jest-dom) et sur les E2E (`tsconfig.e2e.json`). Le projet est à 0 erreur TypeScript : ne pas en introduire. Types manquants : `types/react-simple-maps.d.ts`. Lint : `make lint-front` / `npm run lint` (ESLint 9 flat config `frontend/eslint.config.js` : typescript-eslint recommandé, `react-hooks/rules-of-hooks` et `exhaustive-deps`, variables inutilisées ; inclus dans `make validate` et la CI). Les erreurs échouent toujours ; la baseline `frontend/eslint-baseline.json` est vide (0 avertissement depuis le 2026-11-11) : un avertissement nouveau échoue, il se corrige, il ne s'ajoute pas à la baseline (`node scripts/check-lint.mjs --write-baseline` ne sert qu'à la diminuer). Pas de `eslint-disable` sans motif écrit. E2E Playwright (une centaine de parcours, dont un profil `security` à pile séparée pour 2FA / passkeys / jetons MCP / sauvegarde / notifications, bloqués en démo : connexion, comptes, transactions, import, classement, mois, investissements, paramètres, mobile… et garde console / 5xx sur chaque page) à part : `make test-e2e`, job `e2e` de la CI (un seul job), détails et façon d'ajouter un scénario dans `frontend/e2e/README.md` ; un scénario part de `e2e/fixtures.ts`, pas de `@playwright/test`. Contrôle manuel en plus : mode confidentialité (œil), thème sombre, responsive mobile.

Tests (Vitest + jsdom + Testing Library + MSW ; config `frontend/vitest.config.ts`, `TZ=Europe/Paris`, globals `describe/it/expect/vi`).
- **Tous les tests sont sous `src/test/`**, jamais à côté du code : un test reprend le chemin de son fichier source (`src/pages/AccountDetail/UpcomingCard.tsx` → `src/test/pages/AccountDetail/UpcomingCard.test.tsx`, `src/lib/utils.ts` → `src/test/lib/utils.test.ts`), les tests de traduction d'un domaine (`*.i18n.test.tsx`) sont dans le dossier du domaine. L'outillage partagé est dans `src/test/support/` (jamais importé par l'app, absent du build). Imports par alias `@/…`, jamais en relatif. `src/test/structure.test.ts` échoue si un `*.test.ts(x)` est créé ailleurs.
- Rendu : `renderWithProviders(ui, { route, auth })` de `@/test/support/render` (UIProvider + AuthProvider + ConfirmProvider + MemoryRouter + Toaster ; renvoie aussi `user` = `userEvent.setup()`), jamais un `render` nu pour un composant qui dépend d'un provider. `auth: true` pose un JWT valide une heure (`makeToken({ expInMinutes })` de `@/test/token`, négatif = expiré). `WorkTimeProvider` et les routes d'`App.tsx` ne sont pas montés : les ajouter dans le test qui en a besoin (`App.test.tsx` rend `<App />` avec des pages factices `stubPage` ; `LocationDisplay` de `@/test/LocationDisplay` affiche l'adresse courante pour vérifier une redirection).
- Requêtes DOM par rôle et libellé français (`getByRole("button", { name: "Enregistrer" })`), pas par classe CSS ni `data-testid` sauf dernier recours.
